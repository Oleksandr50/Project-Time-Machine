# Резервные копии Project Time Machine

Backup engine реализован в изолированном экземпляре разработки. При резервном копировании
проекты читаются без изменения исходников. Восстановление через браузер реализовано на этапе 5; порядок и ограничения —
[restore.md](restore.md). Сначала испытайте backup на собственном одноразовом тестовом проекте.

## Работа через браузер

Откройте Backups нужного проекта. Administrator и назначенный Operator могут выбрать
Full backup, Incremental backup или Manual checkpoint, добавить комментарий и поставить
задание в очередь. Viewer просматривает разрешённые проекты и скачивает их архивы.
Очередь показывает состояние, объём, количество файлов, ошибку и кнопку отмены.
JavaScript обновляет прогресс; без него доступна кнопка обновления страницы.

- Full и Checkpoint содержат все объекты выбранного дерева, каждое уникальное содержимое
  один раз внутри архива. Checkpoint — самостоятельная точка, а не ссылка на текущие файлы.
- Incremental содержит новые относительно родителя объекты. Его манифест описывает всё
  целевое дерево и удалённые пути. Даже если CAS уже содержит возвращённый файл,
  отсутствовавший у родителя, этот объект включается в новый incremental.
- Страховые Pre-Restore не выбираются автоматически родителями incremental.
  Для переноса incremental нужны **все архивы родителей** и внешние ключи шифрования.
  Встроенная проверка обходит и проверяет всю цепочку, включая неизменённые старые данные.
- После смены исключений или secret policy нужна новая Full/Checkpoint. При смене key ID
  начните новую Full/Checkpoint. Одинаковый ID ключа нельзя использовать для других байтов.
- Новая точка регистрируется только после проверки пакета, всех объектов и зависимостей.
  Ей соответствует **новый** Recoverable snapshot. Прежние Metadata Only не повышаются.
- «Available» по-прежнему означает наличие файла. Последняя проверка и её ошибки
  показаны отдельно. Проверка при скачивании нового пакета выполняется до HTTP 200.
  Legacy tar.gz остаются доступны с прежними путями и SHA; новый verifier их не импортирует.

Snapshots, File Explorer и Compare видят новую сохранённую структуру. Для обычных
незашифрованных текстовых файлов доступен text diff из CAS. Секретные файлы скрыты.
Для encrypted point текстовый preview отсутствует: браузеру не выдаются расшифрованные
секреты. Метаданные и хеши в служебной SQLite не шифруются этим механизмом.
Новые backup snapshots не выполняют AST-анализ: метрики функций/классов показываются
прочерком. Разделы Analysis/Audit по умолчанию сохраняют последний результат анализа.

## Исключения, источники и SQLite

Применяются исключения проекта из Projects. Каталоги git/venv/node_modules/cache и
обычные backups исключены по умолчанию; обычные пользовательские шаблоны можно изменить.
Собственные code/state/CAS/archives/tmp/keys запрещены независимо от этих шаблонов.
Регистрация и каждое открытие проверяют allowlist и компоненты пути без перехода
по symlink. Небезопасная ссылка, специальный файл или ошибка чтения останавливают
новую копию, а не создают незаметно неполную успешную точку. Ссылка непосредственно
в собственное storage отсекается обязательным исключением.

SQLite распознаётся по заголовку, а не только расширению. DB и её WAL/rollback journal
захватываются через разрешённые read-only дескрипторы в закрытый временный каталог.
Проверяются identities/размеры/mtime/ctime и существование sidecar на всём интервале.
Затем **на частной копии** применяется SQLite Backup API с deadline и integrity_check.
Исходная SQLite не открывается драйвером: приложение не создаёт в проекте SHM и не
делает checkpoint. WAL входит в сохранённую БД; отдельные WAL/SHM/journal в manifest
не публикуются. При нестабильной записи выполняются ограниченные попытки, затем отказ.
Для такого проекта остановите запись штатным способом и повторите backup.

Остальные файлы проверяются на изменение при чтении и между инвентаризациями.
Моментальная согласованность всего дерева не обещается. Для PostgreSQL/MySQL и других
живых сервисов требуются штатные дампы/hooks, которых в этом этапе нет. Пользовательские
БД автоматически не исключаются. Не обещается сохранение ACL/xattrs/владельцев, sparse
размещения или hardlink topology; сохраняются обычные байты, пустые каталоги, mode/mtime.

## Секреты и шифрование

Administrator выбирает политику: сохранять в закрытом локальном storage, сохранять
с предупреждением (по умолчанию) или исключать распознанные секретные пути. Эти политики
не распознают любой возможный секрет: пользовательские glob-исключения остаются важны.
Незашифрованные копии могут содержать секреты; доступ к backup проекта разрешает скачать
весь его архив. Доступа к веб-приложению достаточно только в рамках назначенной роли.

Опциональное шифрование — AES-256-GCM из `cryptography` (новая обоснованная зависимость,
проверена 46.0.7). Файлы шифруются потоково, manifest — AESGCM. Случайный nonce 96 бит
на новую шифрацию, tag 128 бит; AAD связывает project/key/object digest либо заголовок
manifest. Проверяются tag, SHA-256, размеры и связи цепочки. Основание выбора API:
[официальная документация AEAD](https://cryptography.io/en/stable/hazmat/primitives/aead/)
и [потоковый GCM](https://cryptography.io/en/stable/hazmat/primitives/symmetric-encryption/).
Fernet не выбран из-за необходимости удерживать большой файл в памяти.

Создайте ключ отдельно, до выбора его в UI, используя окружение приложения:

```bash
.venv/bin/python -B scripts/generate_backup_key.py "$HOME/.config/project-time-machine-keys/primary.key"
```

Команда создаёт случайные 32 байта, mode 0600, каталог 0700; существующий ключ не заменяет
и байты ключа не печатает. Укажите **только путь** во внешнем PTM_CONFIG:

```json
{"encryption_keys": {"primary-2026": "/home/ptm/.config/project-time-machine-keys/primary.key"}}
```

Это фрагмент: добавьте поле в свой полный конфиг, не заменяйте им разрешённые корни и state.
Ключ принадлежит пользователю службы, не лежит в source/CAS/backups/tmp или каталоге кода.
ID: 1–40 ASCII букв/цифр/`_`/`-`; `plain` зарезервирован. Новая конфигурация читается
при следующем обычном запуске экземпляра; приложение само не перезапускает службы.
Храните отдельную защищённую копию ключа. Потерянный ключ не восстанавливается паролем
администратора. Ротация — новый файл и ID, старый ключ сохранить для старых цепочек.
В конфиге, БД, журнале задания и архиве нет открытого ключа.

Зашифрованы архивные manifest/objects и соответствующие CAS-объекты. Уже существующие
незашифрованные копии не переписываются при смене политики. Во время захвата допустима
частная временная plaintext-копия (особенно SQLite); каталог 0700, файлы 0600,
после штатной операции удаляется. При аварии временные/orphan данные могут сохраниться.
Это не шифрование диска: применяйте защиту диска/ОС для state, tmp и оставшихся после сбоя
файлов. Приложение не обещает безопасное стирание SSD или резервную копию внешнего ключа.

## Формат и хранение

Формат v1: ZIP_STORED `.ptm`, `format.json`, `manifest.bin`, `objects/<SHA-256>`.
Не используется extractall. Manifest: version/project/point/UTC/actor/comment/type,
полное дерево, size/SHA/mode/mtime/category/SQLite, omissions/exclusions/secret policy,
parent ID + SHA archive/manifest, локальные objects и deleted paths.
В encrypted package manifest.bin = nonce(12) + AESGCM ciphertext/tag, AAD — canonical
format.json. Объект = `PTMGCM1\0` + nonce(12) + ciphertext + tag(16), AAD
`PTM1:object:<project_id>:<key_id>:<plaintext_sha256>`. Для plain — исходные байты.
Неизвестные версии отвергаются; header и manifest имеют ограничения 4 KiB/16 MiB,
дерево — 100 000 записей, цепочка — 256 точек. Предел цепочки требует периодической Full.

Проверяются duplicate members/JSON keys, абсолютные пути, `..`, drive/UNC/backslash,
Windows reserved names, регистр коллизий, file/directory conflict, links/devices,
неожиданные ZIP entries, compression/encryption flags, размеры и digest/tag.
Доверенный SHA всего архива хранится в project history SQLite. Это защита от повреждения
и подмены файла при сохранной доверенной БД, не подпись против владельца всей машины.

Новые архивы находятся в `<project.backup_path>/engine-v1/`, 0700/0600. Старые большие
архивы не перемещаются, их каталоги и права автоматически не изменяются.
CAS: `<content_dir>/projects/<id>/<key_id или plain>/<sha[:2]>/<sha>`, с отдельным
namespace на проект/ключ. Одинаковые файлы повторно не пишутся в CAS. Full всё же
содержит свой полный набор объектов для независимости от других архивов.
CAS и portable archives дублируют данные намеренно; объём архива на Dashboard не
включает CAS. Сжатия и block-level dedup пока нет. Incremental экономит содержимое,
но каждый файл полностью перечитывается для достоверного SHA.

Запись объекта/пакета: private temp → fsync → atomic link без перезаписи → directory fsync.
Публикация backup row, нового snapshot и ссылок — одна транзакция project SQLite.
Внешний metadata JSON для нового backup не дублирует manifest; authoritative metadata
находятся в manifest и project DB. Существующие JSON старых metadata snapshots сохранены.
Нет общей атомарной транзакции между файловой системой и SQLite: после аварии возможен
непривязанный `.ptm`/CAS/temp. Он не становится успешной точкой автоматически и не
удаляется автоматически; сохраните его для отдельного разбирательства. Удаления исходных
файлов и автоматического отката проектов в этом коде нет.

## Очередь, расписание и очистка

Настройки: `max_parallel_jobs` (по умолчанию 2, максимум 8), `job_poll_seconds` (2),
`backup_reserve_bytes` (64 MiB сверх оценки требуемого места). Проверяются отдельно tmp,
content и archive volumes; оценка намеренно консервативная, особенно для SQLite/Full.
ENOSPC/I/O не публикуют успешный point. Одна межпроцессная project lock объединяет
analysis/backup/verify/cleanup и предназначена также для Restore этапа 5.

Один dispatcher получает file lock; несколько workers bounded pool. Jobs/schedules —
в registry SQLite. Пара ежедневное/еженедельное задаёт интервалы 24h/7d от сохранения,
UTC; выбора часа суток пока нет. Поддерживаются backup, metadata snapshot, verify,
cleanup. Пропущенные интервалы объединяются в одно задание, unique(schedule,time)
и транзакция продвижения расписания предотвращают повтор при рестарте.

Queued jobs продолжаются после запуска. Running job никогда не повторяется вслепую:
если point с job ID уже закоммичен и проверяется — success, иначе interrupted и новый
запуск только новым заданием. Если worker завершился, но запись статуса временно
не удалась, dispatcher повторяет сверку committed point после возвращения доступа к БД,
не сам backup. Временные busy/source-change/SQLite instability ошибки
повторяются максимум три раза с persisted backoff. Отмена кооперативная; проверяется
также перед публикацией. Права/роль/auth_version/доступность проекта повторно проверяются
worker, отозванные права останавливают queued/running работу. Shutdown подаёт stop и
ждёт свои workers; не управляет внешними процессами. Во время отдельных AST/OS I/O
шагов немедленная отмена не гарантируется.

Очистка выключена по умолчанию. Administrator с повторным вводом пароля включает её
в policy, задаёт keep_last/min_age_days и может настроить schedule. Ручная очистка
требует слово `delete`. Retention оставляет недавние, protected и всех их предков;
сначала проверяет сохранённые цепочки. Legacy tar не удаляет.

Для каждой удаляемой новой точки: durable deleting → unlink archive + fsync →
snapshot unavailable/удаление content references → удаление CAS без других ссылок →
deleted. Все metadata/history/backup rows остаются. Journaled deleting завершается
после перезапуска; до завершения удаления новый backup такого проекта блокируется.
Непривязанные CAS от ранее отменённых/аварийных работ автоматически не собираются;
для них требуется отдельный будущий maintenance/import инструмент. Не удаляйте storage
руками и не заменяйте историю устаревшей копией при работающем dispatcher.

Поддержка проверена на локальной Linux/POSIX FS, в нативной установке и Docker с bind
volumes. Native Windows filesystem jobs остаются fail-closed: reparse-safe backend
не реализован. Подготовлен запуск через WSL2, но реальное Windows/WSL2 испытание ещё нужно.
NFS/SMB/distributed dispatcher, физическая power-loss проверка и штатные hooks других
БД не проверялись. Копия на том же диске не защищает
от отказа диска: переносите полный набор архивов и отдельный ключ на другой носитель.
