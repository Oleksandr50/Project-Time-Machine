# Восстановление проектов — этап 5

Работайте сначала с одноразовым тестовым проектом. Реальные файлы меняются только
после входа с правом восстановления, проверенного preview и явного подтверждения.
Приложение не останавливает и не запускает чужие процессы и службы.

## Через браузер

1. Выберите проект и откройте Restore. Administrator может восстанавливать проекты;
   Operator — только назначенный проект с отдельным can_restore. Viewer читает историю.
2. Выберите Full/Incremental/Checkpoint, Recoverable snapshot или зарегистрированный
   старый tar.gz. Metadata Only, Incomplete и непроверяемое содержимое не восстанавливаются.
3. Выберите весь проект, отдельные файлы (относительные пути, один на строку) либо новый
   каталог с абсолютным путём. Новый каталог должен отсутствовать. Полный режим также
   умеет заново создать исчезнувший исходный каталог зарегистрированного проекта.
4. Нажмите «Проверить и показать изменения». Приложение проверяет все архивы цепочки,
   digest/tag/размеры, доступ, свободное место и текущее дерево. Preview показывает точку,
   комментарий, цель и добавляемые/заменяемые/удаляемые пути с пагинацией/сортировкой.
5. Самостоятельно штатно остановите запись и службы этого проекта. Обнаруженные PID
   показаны без argv/env; такие процессы блокируют применение. Проверка /proc может быть
   неполной — отсутствие PID не гарантирует отсутствия писателей.
6. Проверьте список, поставьте подтверждающую отметку и введите точное слово `RESTORE`.
   Создаётся постоянное задание. Прогресс/отмена — в Backups, результат — в Restore.

Preview живёт 15 минут, привязан к пользователю, конкретной активной сессии/auth_version,
проекту, точке/всей цепочке, путям/исключениям/политике и текущим байтам/метаданным.
При изменении дерева, корней, точки или политики нужен новый preview. Token используется
один раз; в URL только public preview ID, секретный token передаётся формой, хранится digest.
Подставленные user_id/role/destination в confirm не меняют сохранённый план.

Точки переносимого backup сохраняют mode/mtime файлов и каталогов. У CAS-only snapshot
старого формата этих полей нет: используются 0644/0755 и доступный mtime, родительские
каталоги выводятся из путей. Права владельца, ACL/xattrs, hardlink topology, sparse-файлы,
спецфайлы и SUID/SGID не обещаются. Новый корневой каталог создаётся закрытым, 0700.

## Область изменений

Используется объединение исключений текущего проекта и выбранной точки. Обычные
исключения настраиваются в Projects. Системное storage приложения и собственные workspace
исключены обязательно. Вложенные зарегистрированные проекты (включая отключённые)
сохраняются; регистрация нового пересекающегося проекта во время restore запрещена.
Многокомпонентные правила вроде `outer/backups` применяются и ко всем потомкам.

При режиме отдельных файлов соседи не меняются. Необходимые каталоги создаются;
невыбранные файлы не удаляются для замены каталога файлом. Конфликт такого рода
останавливает операцию до подтверждения. Для полного режима исключённые каталоги и
неархивировавшиеся секреты остаются. Preview, а не слово «полный», определяет точную область.

Разрешены только явно настроенные корни, без traversal/символических ссылок и
credential-путей `.ssh/.aws/.gnupg/.codex`. Проверяются не только регистрация, но и
каждое открытие/применение; подмена корня/родителей или другого проекта блокирует запись.
Дополнительный каталог находится вне действующих зарегистрированных проектов; существующий
произвольный destination нельзя передать как alternate. Нет способа обойти это через POST.

## Страховая копия

До изменения пользовательских путей создаётся самостоятельная проверенная Pre-Restore
Backup, автоматически protected. Она использует **текущие** secret/encryption настройки.
Все перезаписываемые файлы должны быть в страховке с правильными байтами либо корректной
SQLite Backup API копией. Если политика исключает затрагиваемый секрет, overwrite
запрещён. Administrator выбирает безопасное хранение (при необходимости encryption),
затем создаётся новый preview; приложение не обходит secret policy автоматически.
Непотревоженные исключённые секреты в страховку не добавляются вопреки политике.

Целостность страховки проверяется при создании и непосредственно перед apply.
При ошибке/нехватке места/потере ключа записи в пользовательские файлы нет.
Если новая цель ещё отсутствует, страховая точка описывает её пустое прежнее состояние.
Manifest содержит restore_context с целью/существованием/operation ID. Страховку другого
destination нельзя случайно применить ко всему исходному проекту. Для изучения её можно
развернуть в новый каталог; для прерывания используйте recovery именно её операции.

Страховые точки не выбираются автоматически родителями последующих incremental.
Следующий incremental продолжает последнюю обычную Full/Incremental/Checkpoint,
учитывая изменения после restore. Все старые metadata-only и backup записи сохранены.

## Как выполняется применение

Один process project lock и durable lease охватывают verification, insurance, staging,
apply и проверку результата. Backup/analyze/retention для того же проекта не выполняются
одновременно; после прерывания блокировка остаётся в SQLite до решения пользователя.
Глобальный предел параллельных задач продолжает действовать. Restore нельзя запланировать
в scheduler или вызвать прямым POST /restore: только одноразовое подтверждение wizard.

Staging/undo создаётся после подтверждения на файловой системе цели:

- для существующей цели — `<project>/.ptm-restore-<operation-id>/`;
- для новой — такой каталог рядом с целью, внутри разрешённого родителя.

Это намеренное исключение из общего temp_dir: для rename нужен тот же filesystem/mount.
Путь выведен из проверенной цели, а не принимается от браузера. Общий temp_dir по-прежнему
настраивается и используется для SQLite/backup временных файлов. Workspace — 0700,
маркер — 0600, nonce/inode проверяются. Данные staging читаются и пишутся через закреплённый
приватный FD. Если имя workspace подменено, нет перехода по ссылке в посторонний каталог.
Внутренние `/proc/self/fd` capabilities scoped, закрываются/reset в finally; URL не может
создать такую capability или открыть произвольный /proc path.

Все payload заранее сохранены и сверены в staging. SQLite integrity_check работает
на копии в закрытом application temp, не на текущей рабочей базе. Затем каждый шаг
сначала коммитится в SQLite journal, только потом выполняет rename + fsync каталогов.
Старые inode уходят в undo; новые устанавливаются no-clobber rename. Проверяются
root/parent IDs, реальные байты и отсутствие подмены. Финальная проверка сверяет
восстановленные SHA, размеры, mode/mtime и состав managed-дерева.

**Общая атомарность существующего дерева не гарантируется.** Между переносом старого
файла и установкой нового возможно отсутствие имени. Поэтому работающие с проектом
службы должны быть остановлены. Новый полностью staged каталог публикуется одним
Linux renameat2(RENAME_NOREPLACE); неподдерживаемая FS/cross-mount отвергается.
Основание: [Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html).

## Сбой и recovery

Автоматического rollback нет. После сбоя откройте Restore:

- **Undo**: проверяет прежние inode/байты, возвращает оригиналы и отдельно сохраняет
  убранные новые inode. До перезаписи частичного состояния создаётся новая проверенная
  protected страховка. Даже повторное прерывание undo допускает новый явный preview.
- **Из страховой точки**: используйте, если undo недоступен или файлы изменились после
  сбоя. Новый preview показывает актуальные удаления/замены, создаётся новая страховка
  частичного состояния; прежний журнал остаётся как superseded. Если новую recovery
  отменили или она отклонилась до apply, прежняя interrupted lease снова активна.

После рестарта running restore не повторяется. Committed/rolled_back — только
исторический результат, остальные незавершённые стадии становятся interrupted.
Startup не пишет в source и не откатывает его. Потеря финального статуса job сверяется
dispatcher с журналом; SystemExit worker не выдаётся за успех и не убивает dispatcher.
Два preview одной recovery нельзя одновременно подтвердить как конкурирующие задачи.

Если после прерывания изменены затронутые файлы, undo их не перезаписывает.
Нужен новый insurance preview с актуальным сравнением. Неизвестные workspace не
обходятся и не удаляются. При утрате/повреждении самой страховки, ключа или неизвестном
корне операция отказывает; не редактируйте registry/journal вручную и не удаляйте undo.
Новая восстановленная из страховки цель обычно сохраняет свой корневой каталог;
точный undo нового каталога возвращает его к отсутствию, если его inode/состав не изменились.

## Сохранённые undo-данные

После success и после undo workspace **сохраняется по умолчанию**. Это сохраняет и
позднюю запись внешнего процесса в старый открытый inode; автоматический unlink мог бы
потерять такие данные. Тест отдельно пишет в старый FD после commit и проверяет сохранение.
Workspace исключён из snapshots/backup/log discovery без возможности снять исключение;
права 0700 сохраняются. Обычная retention архивов его не удаляет.

Цена — дополнительное место и plaintext-копии старого/временного содержимого рядом
с проектом, даже если переносимые архивы/CAS зашифрованы. Нужна защита ОС/диска и
ограничение доступа к источнику. Встроенного безопасного GUI cleanup/export workspace
в этом этапе нет: не удаляйте его вручную во время незавершённой операции. Review/cleanup
требует отдельного обслуживания после проверки, что процессы не держат старые inode
и защищённая страховка действительно доступна. Pre-Restore архивы также protected.

## SQLite и ограничения

Новые SQLite точки — согласованные Backup API копии, SHA и integrity проверяются.
WAL/SHM/journal текущей восстанавливаемой базы явно перечисляются как удаления в preview;
их предыдущее логическое состояние покрывает страховая SQLite копия. Отдельное
восстановление WAL/SHM/hot journal поверх другой базы запрещено. Старый tar с DB+WAL/journal
не получает обещание согласованности: требуется отдельный verified import, которого пока нет.
[Описание SQLite Backup API](https://www.sqlite.org/backup.html).

Для других живых БД нет database-native hooks. Остановите запись и подготовьте штатные
дампы самостоятельно. Результат — сохранённые байты, не гарантия транзакционной
согласованности произвольного сервиса.

Поддержка проверена на локальном Linux/POSIX с /proc и renameat2, через нативный installer
и реальные Docker bind volumes с non-root/read-only rootfs. В контейнере обнаружение
процессов всегда помечено неполным: процессы хоста не видны в его PID namespace.
Native Windows/reparse, реальная WSL2, NFS/SMB и другие mount-варианты ещё не испытаны.
Нет восстановления symlink/device/socket,
автостарта служб, произвольного импорта архивов, automatic resume/rollback.
Лимиты: 100 000 entries/point, chain 256, manifest 16 MiB, restore preview/spec 32 MiB,
выборка отдельных файлов до 1000 путей. SQL integrity имеет deadline 20s, backup —
прежние ограничения. Предварительная проверка места консервативна для tmp, target и registry.
Согласованная backup цепочка и отдельная защищённая копия ключа должны храниться вне
того же физического диска; checkpoint кода не является защитой от отказа носителя.
